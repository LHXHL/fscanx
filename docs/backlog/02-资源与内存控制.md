## BL-MEM-001 修复 ReadRawWithSize 池污染数据竞争

- 模块：资源与内存控制

- 关联模块文档：docs/modules/02-资源与内存控制模块.md

### 背景

`ReadRawWithSize`（Plugins/webScanTask.go:681）存在池污染问题：

1. `raw := BufBuildPool.Get()` 后 `return raw.Bytes()`——返回切片与池化 buffer 底层数组共享，但 buffer 已被 `Put` 回池。任务 A 返回的 body 会被任务 B 的写入覆盖。
2. defer LIFO 顺序：先注册 `defer raw.Reset()`（685 行）、后注册 `defer BufBuildPool.Put(raw)`（686 行），返回时**先执行 Put 后执行 Reset**——A 的 Reset 会清掉 B（已从池中拿到该 buffer）正在写的数据。
3. 错误路径同样受影响：webScanTask.go:725 `return raw.Bytes(), err` 也返回池化内存；调用方 DoWebScan（443-445 行）忽略 err 后仍继续使用 body。

同属正确性的附带修复：`DoWebScan`（webScanTask.go:422）每次请求对共享 `lib.Client`/`lib.ClientNoRedirect` 赋值 `client.Timeout`，与 InitHttpClient（client.go:82-88）的初始化重复，且是并发数据竞争，删除该行。

### 范围

- ReadRawWithSize 所有返回路径（正常 + 错误）拷贝数据后返回，池化 buffer 内存不逸出池外
- 删除 DoWebScan 中对共享 client.Timeout 的赋值行
- 新增并发单测覆盖正常路径与错误路径

- 不改指纹读取上限（属 BL-MEM-002）
- 不删除 webScanTask.go:739-769 注释死代码（记入 docs/modules/02-资源与内存控制模块.md「后续开发事项」节）

## BL-MEM-003 日志管道 IO 优化、qqwry 按需映射与历史欠账清理

- 模块：资源与内存控制
- 优先级：P1
- 状态：已完成
- 当前阶段：持续迭代
- 价值：去掉每条结果一次 fsync 的日志写放大（目录扫描上线后日志量将放大多倍，IO 管道会背压到全部扫描 worker）；qqwry 从 27MB 常驻改为按需映射，VPS 省内存；清偿 BL-MEM-002 显式记录的死代码欠账。
- 关联模块文档：docs/modules/02-资源与内存控制模块.md
- 关联计划：plans/2026-11-13-BL-MEM-003-管线优化.md
- 关联代码：common/log.go、Plugins/qqwry.go、Plugins/scanner.go、Plugins/webScanTask.go、Plugins/portscan.go、main.go
- 验收状态：已验收

### 方案（B0 架构 review 产出 + 独立审查修订，2026-11-13）

- **做什么**：三件事——①日志写出管道去 fsync 加缓冲；②qqwry.dat 从"启动即 io.ReadAll 全量常驻 27MB"改为 Linux 下 mmap 按需映射；③删除 BL-MEM-002「不做」节与 02 模块文档「后续开发事项」记录的死代码欠账及若干无效/冗余代码。
- **为什么**：
  ① 每条结果日志都 `fl.Sync()`（common/log.go:173 强制刷盘），且 `Results` 是无缓冲 channel（log.go:18）——终端打印/磁盘写的任何毛刺都直接背压到所有扫描 worker。扫描结果非数据库，崩溃丢尾部几行可接受。
  ② qqwry.dat 27MB 在 `init()` 无条件 `io.ReadAll`（Plugins/scanner.go:28、Plugins/qqwry.go:252）且加载错误被吞（`Czdb, _ =`）。BL-MEM-002 曾决策"不动"（理由：二分查找需随机访问，功能必需静态内存）——mmap 恰好同时满足"随机访问"与"省常驻内存"：映射返回 []byte 类型不变（Reader 代码零改动），物理内存由 OS page cache 按需换入，无归属地查询时几乎零 RSS。该决策是演进而非推翻：数据形态与查找逻辑不变，只换装入方式。**平台边界（独立审查实测）**：`syscall.Mmap` 在 Windows 的 Go 上不存在（编译期失败，运行时回退救不了）——采用分平台文件：unix（linux/darwin）走 mmap + 失败回退 ReadAll，windows 直接 ReadAll（开发机场景，内存不敏感）。
  ③ 死代码：portscan.go 4 个注释旧实现约 250 行、webScanTask.go 4 个注释旧 ReadRawWithSize 约 85 行、main.go MemStats 调试块、log.go 旧签名注释、icmp.go.bak 残留文件、`mylib/simplehttp` 整包（02 模块文档「后续开发事项」记录的无 import 死包，本轮清偿）；`alivePortResList` 恒空死逻辑（scanner.go:265,392 条件恒真）；`targetInfo = nil` 无效语句（webScanTask.go:320）；DoWebScan 对 resp.Body 双重 defer Close（webScanTask.go:425-440）。git 有历史，删净降阅读噪音——目录扫描将复用这些文件的读取模式，先修干净防复制坏样本。
- **怎么做**：log.go 删每行 Sync——**WriteString 保持直写 os.File 不引入 bufio**（一次 `write(2)` 后数据即在内核页缓存，进程被 Ctrl+C 杀死不丢已写行，仅断电丢尾部可接受；bufio 把数据挪入用户态缓冲、进程死即丢，是为省 syscall 引入的新风险，而每行一次 write 的 μs 级成本相对 fsync 的 ms 级可忽略——第三轮再审撤销原 bufio + 中断 flush 方案）；qqwry.go 拆 `qqwry_load_unix.go`（mmap + 回退）/ `qqwry_load_windows.go`（ReadAll）两个分平台文件，NewQQwry 调平台装入函数，顺带记录加载错误不再吞；死代码与无效语句直接删除，双重 Close 去重；同步更新 02 模块文档基线表 qqwry 行与「后续开发事项」。
- **为什么这么做**：三件事互不耦合但同属"管线健康"主题，合并一个 item 避免碎片化；都不改变任何扫描行为与输出格式（纯基础设施），故验收以"输出逐行一致 + 构建测试通过"锚定。
