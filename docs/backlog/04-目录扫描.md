### 方案（B0 讨论定稿 + 独立审查修订，2026-11-13）

- **做什么**：新增 `-dir` 开关的目录扫描子系统——端口/Web 扫描发现的每个存活站点，用 go:embed 内置路径字典（`-dirf` 可覆盖）逐路径探测，识别出产品指纹的结果以同构 `[+] Product` 行输出到 result.txt。
- **为什么**：现有指纹识别只看站点根路径（WebScanWorker 从根 URL 起扫），大量 Web 资产挂在二级路径下（OA、后台、运维控制台），根路径是默认页或反代时完全不可见。用户在实战中需要"隐藏后台"维度的资产发现。
- **怎么做**（六个已定决策）：
  1. **调度单元反转 + round-robin 轮询环 + 两阶段停机**：单 goroutine 调度器维护站点轮询环（每站点：URL 字符串 + 路径下标 int + 在途计数 int），循环遍历发射 `(site, path[idx])` 任务，该站点在途请求 >0 则跳过——任意时刻单站点在途请求 ≤1，N 个站点请求在时间上交错，不集中轰任何站点（朴素实现"扫完站点A全部路径再扫B"等效于对每站点顺序 DDOS）。调度器在"无站点可发射（全部在途或已扫完）且未停机"时**阻塞等待、在途归零时唤醒，禁止自旋空转**（VPS 单核场景烧 CPU）。**停机协议**（解决"动态注册"与"全扫完 close"的竞争）：调度器不因"暂时无活站点"退出；主流程各模式（Scan / ScanFromReader / masscan）收尾时先调用"关闭注册"（此后新站点不再入环），再等调度器排空（现存站点全部扫完、聚合行全部输出）后才结束。在途计数递减与 LogWG.Done 一律 defer 化（panic-safe：worker panic 不会把站点永久卡在"在途>0"导致全局卡死）。
  2. **三层判定：404/5xx 短路 → 302 同前缀跟随 → 首页指纹差集**：
     - **短路**：404/403/5xx 与 3xx 一律不进引擎直接丢。3xx 是真机实测教训（2026-11-14 验收反馈）：同源同前缀规则拒绝跟随时拿到的是 302 响应本身，其 Location/Server **响应头**会被指纹引擎匹配出无关产品（Location 含 "thinkphp" 字样即误报 thinkphp——指纹来自跳转指令而非任何页面内容），且 302 默认页标题与首页呈现必然不同、差集拦不住；跟随成功的落地响应状态码才进入判定，限跳截断的落地 3xx 同语义丢弃。403 屏蔽（2026-11-14 用户决策）：全站 403 的 WAF/安全设备使每条路径都变成"403+Server 头指纹"噪声；401 保留（后台认证墙是路径存在的更强信号）；
     - **统一指纹过滤**：其余任何状态码一律过现有指纹引擎 `Engine.DetectContent`（吃原始响应含响应头）。200 型软 404（自定义 404 页返回 200）几乎匹配不出产品名，免检测地免疫；401/403 的价值交给响应头特征抓住（如 Tomcat Manager 401 的 `WWW-Authenticate: Basic realm="..."`）；
     - **302 同源同前缀跟随（发射端过滤，管流量）**：301/302 先判 host（Location 为绝对 URL 且 host 与原站点不同 → 不跟随，防 CDN/跨域绕过），再判 path 前缀（仅同前缀才跟随：`/druid` → `/druid/login.html` 跟随；`/randompath` → `/login` 丢弃）。软 404 站点上无脑跟随会把跟随请求放大 70 倍，违背"不轰单站点"初衷；
     - **首页呈现差集（出口端过滤，管正确性）**：以（指纹, 标题）**二元组**为判定单位——路径的有效呈现组合与首页扫描已见过的呈现集合完全重合则丢弃；出现新组合（新指纹或新标题）才输出。**判定与输出解耦**（Mode D 实现前修正，2026-11-13）：输出行带该路径识别出的**完整指纹列表**而非差集部分——WordPress 后台场景差集为空，只打差集会输出无指纹的空行，违背"同构 Product 行带指纹"的初衷；完整指纹保信息量，二元组只承担防误报判定。呈现 key 的指纹部分**必须排序后拼接**（指纹引擎输出顺序非确定为 pre-existing，MEM-003 实证，不排序则去重/差集判定失效）。原理：软 404 的落地页（登录页/首页）必然是首页扫描已跟随访问过的页面（WebScanWorker 现有跳转逻辑本来就会走到），其呈现与首页完全相同——即使同前缀规则漏拦，误报也出不了出口。**用二元组而非纯指纹**（第三轮再审修正，用户决策 2026-11-13）：纯指纹差会误杀"同产品后台入口"——WordPress 站的 `/wp-admin` 后台与首页同指纹不同标题，正是 path.txt 通用路径（/admin、/wp-admin、/console）的核心价值场景，靠标题差异救回。已知残余误报窗口（接受）：软 404 回跳页标题恰好与首页不同。
  3. **站点聚合输出 + LogWG 顺序契约**：输出行与首页指纹行同构——`[+] Product <url>\t<状态码>\t(<title>)\t<指纹列表>`（TAB 分隔，指纹无方括号），url 用原始请求路径（如 `http://ip:port/seeyon/`），下游 FscanOutput_v3.4.py 零适配。聚合器站点内按（指纹列表+标题）去重，同一 key 多条路径命中时 url 取**首个命中路径**；聚合器生命周期 = 该站点目录扫描时长，站点全部路径完成时一次性输出 0~几行并释放（内存峰值只与在环站点数相关，几十 KB 级）。**顺序契约**：站点聚合输出行必须先 `LogSuccess`（内部 LogWG.Add）发出，之后该站点最后一个任务才 `LogWG.Done`——保证 main 的 `LogWG.Wait()` 返回时不存在"还没来得及发送的聚合行"（否则 close(Results) 后发送即 panic）。
  4. **注册点 = WebScanWorker 返回后**（统一入口，覆盖主模式端口扫描派生 / `-u,-uf` URL / `-std/-msc` 管线三类入口；按最终确认存活的 URL 去重）。**返回 err（站点连接层不可达）不注册**——否则 70 条注定超时的请求要白等 9s×70≈10.5 分钟并拖死收尾排空。不选 DoWebScan 内部注册：它会被跳转链重入多次（scanType 1/3），且注册时首页扫描链可能仍在途，与目录请求同 host 并发时受 `MaxConnsPerHost=1` 排队、挤占 9s 总超时。**首页呈现集合的取得需改造指纹收集路径**：现状 DoWebScan 把指纹拼进输出字符串即丢弃（webScanTask.go:566-576），函数不返回——需增加返回值或收集器；集合定义为首页扫描链全部调用（初次 + 跳转跟随 + https 重试）的（指纹,标题）并集，漏收任何一次差集即有漏洞。
  5. **字典 go:embed 内置 + `-dirf` 覆盖，默认关闭**：内置字典取自根目录 path.txt（70 条，CRLF 行尾、末行无换行——解析必须 TrimSpace，否则每条路径带 `\r` 全部请求失败）。默认不开启：目录扫描使对目标请求量放大约 70 倍，属重大行为变化，须显式 `-dir`。
  6. **模式交互**：`-m webpoc` 模式下 WebScanController 直达 PocScan 不经 WebScanWorker，`-dir` 在该组合下静默无效（不注册、无目录流量）。HTTP client 用目录扫描专用 `http.Client` 包装（共享现有 Transport，自带 `Timeout=WebTimeout`、CheckRedirect 限 3 次）；现有 `MaxConnsPerHost=1` + `DisableKeepAlives` 与单站点在途≤1 自洽，不构成瓶颈。worker 池默认 16（channel 容量=worker 数）。开启 `-dir` 时打印一行总量提示（站点数 × 路径数），让使用者理解扫描时长增加。
- **为什么这么做**：
  - 均摊机制否决两个备选：①朴素"每站点串行扫完再下一个"——对单站点等效 DDOS，违背设计初衷；②复用现有 `WebScanRateCtrlCh` 总闸门——60 并发可能瞬间全打在同一站点，总闸门控制全局吞吐而非单站点压力，必须新增 per-site 维度调度。
  - 输出方案否决"并入首页指纹行"（阻塞首页输出、Ctrl+C 丢信息、路径来源丢失）与"独立结果文件"（下游脚本要适配、VPS 双文件运维），站点聚合 + 同构行是唯一同时满足实时性/低内存/零适配的。
  - 302 处理否决"无脑跟随"（302 型软 404 盲区：统一登录页站点会全路径误报）与"全不跟随"（丢掉 /druid → /druid/login.html 这类真实子路径跳转发现），同前缀规则两者兼顾且实现约 10 行。同前缀与差集两道防线互补不冗余：单靠差集，软 404 站点要打满全部跟随请求才轮到出口过滤（流量放大）；单靠同前缀，存在漏拦窗口（同前缀的意外跳转）且无出口兜底。差集规则的"指纹仅来自页面内容、与路径名无关；误报的本质是归因错误而非识别错误"由用户质询澄清后定稿。

- 内置字典 embed（内容取自根目录 path.txt，解析 TrimSpace；embed 文件放 Plugins 包内，go:embed 不能引用包外文件，根目录 path.txt 去留实施时定）

### 不做

- 不做通用目录爆破/文件枚举（无字典 fuzz、无扩展名猜测）——定位是指纹识别的补充维度
- 不做随机路径 baseline 软 404 检测（200 型软 404 已被指纹过滤免疫；302 型已被同源同前缀 + 呈现差集双重防御；baseline 每站点多一次请求，与省流量矛盾）
- 不做 401/403 无指纹输出（攻击面清单模式）——预留演进
- 不做跨域跳转跟随与"跳转目标当新站点注册"（跳到外部统一认证域/CDN/他域 host 的响应不跟随不输出）
- 不做站点级目录扫描时限与 Ctrl+C 时聚合器紧急输出（慢站点最坏 70×9s≈10.5 分钟拖长收尾、中断时聚合器中已命中未输出的行丢失——均记为接受的取舍；总时长显著增加是均摊的预期代价）
- 不做同 host 双 scheme（http/https）站点去重（`-dp` 域名注册两个站点、同后端时目录流量双倍——与现有首页扫描行为一致，记为预期）
- 不做目录发现结果驱动 POC 精准触发（指纹→POC 管道是全项目独立缺口，另行立项）
- 不做 favicon 主动探测恢复（独立演进项）
