# BL-POC-002 合并式 poc 加载 + 绑定关系外置

## 目标

新增 poc 零编译：yml 丢进二进制旁 `pocs/` 即生效；`-pocpath` 从替换改追加（内置不再失效）；绑定关系数据 binds.yaml 加载就绪（003 消费）。

## 方案（已与 backlog item 对齐）

1. `PocScan/WebScan.go` initpoc 重构三层合并：内置 embed → 二进制目录 `pocs/`（os.Executable 推导，存在才加载并打印一行）→ `-pocpath` 追加。同名 poc 后加载覆盖先加载（外置修正内置），**替换保位**（slice + index map）保证顺序稳定可测。
2. 新文件 `PocScan/binds.go`：`Bind{Product, Always, Pocs}` schema（product=fingers 引擎输出产品名；pocs 取 poc 的 yaml name 字段）；`LoadBinds(path)` 文件不存在返回 nil 正常态。initpoc 顺手加载二进制旁 `binds.yaml` 进全局 `PocBinds`（003 直接消费）。
3. `PocScan/binds_test.go`：不存在/正常+always/空文件/非法 yaml 四组单测。

## 设计决策（收尾同步进模块文档）

- **基准目录=二进制所在目录**而非工作目录：内网工具目录习惯（exe 与 pocs/ 同放），cd 到别处跑不影响；go run 开发场景无妨（用 -pocpath）。
- **替换保位而非 map 重排**：filterPoc 遍历 AllPocs 的顺序影响请求顺序与测试可复现性。
- 原内置加载的错误忽略行为（`poc, _ := lib.LoadPoc`）保持不变，只挪结构不加戏。

## 风险

- 二进制目录推导在 `go run` 下指向 temp——开发者场景用 -pocpath，不影响用户。
- 外置 poc 质量不可控（手写 yml 语法错）——沿用原静默跳过行为；004 web 端落盘前校验兜底。

## 验证方式

/tmp 隔离目录三 case（python http.server 18923 计数）：
- A 验收1：exe 旁 pocs/test-echo.yml（新名）→ `-m webpoc -pocname test-echo` → server 见其 path 请求
- B 验收2：pocs/ 放与内置同名 poc-yaml-74cms-sqli（path 改 /overridden-marker）→ `-pocname 74cms-sqli` → 只见新 path 不见原 path
- C 验收3：无 pocs/ 的目录跑 `-pocname all` 计数 ≥1168（内置未失效）+ `-pocpath` 追加目录的 poc 被执行
- D 验收4：`go test ./PocScan/ -run TestLoadBinds -v`
- 回归：case 001 空 pocname 全量计数不变量级；build+vet+test 全过
