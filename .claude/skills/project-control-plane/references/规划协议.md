# 规划协议：Mode B0 / B / C / G / H

进入前已完成路由（SKILL.md）。含模糊检测与各规划 Mode 流程。backlog 格式与状态值见 `项目约定.md`。

**按 Mode 读节**（文件 70 行，五 Mode 互斥）：
- 路由模糊判定 → 「模糊检测（路由依据）」
- 需求澄清 → Mode B0（3-5 轮轻量访谈）
- backlog 生成 → Mode B + `项目约定.md` 的编号/状态/item 格式
- 阶段规划 → Mode C
- 阶段过渡 → Mode G
- 高风险共识 → Mode H（全文，需完整 Planner→Architect→Critic 流程）
- 通用 → 「规划类失败处理」

## 模糊检测（路由依据）

**specific** 信号（有其一即具体）：引用具体文件路径/函数符号 / 有编号可测验收标准 / 点名 API 端点、数据库表或 UI 组件 / 引用边界清晰的模块文档。

**vague** 信号：宽泛动词无具体范围（"完善 XX 管理""优化系统"）/ 验收标准是套话（"功能正常""编译通过"）/ **证伪失败**——任一标准问"用什么测试证明它没实现"无答案，则它不是标准 / 核心实体不稳定（同一概念多个名字）/ 范围可小到一行也可大到重写模块。

模糊时：无 item → 进 B0；有 item → 进 B0 或 H。不静默推进；用户坚持则按其决定，但把歧义记为风险。

## Mode B0：需求澄清（3–5 轮轻量 Socratic 访谈，非 20 轮 deep-interview）

1. **定问题空间**：一句话目标（"完成时用户能做什么？"）；为谁解决什么问题；答不出就问"没有它用户卡在哪一步？"。
2. **稳定实体（ontology）**：命名关键名词；实体漂移要点破——"上一轮 X 这一轮 Y，是同一概念吗？"；先稳定实体再谈功能。
3. **边界与不做**："边界是什么？什么一定不做？"；依赖哪些已有模块/外部系统；显式假设（登录态、匿名访问等）。
4. **可测验收**：每条问"用什么具体行为判断满足？"；拒绝"功能正常"——要求具体输入/输出（如"POST /api/products 返回 201 且 DB 有对应行"）。
5. **第 3 轮起简化检查**："只做 20% 工作拿 80% 价值的那 20% 是什么？"→ 拆 P0（当前必须）与 P1–P3。
6. 产出 backlog item 草稿（格式见 `项目约定.md`）：模块/优先级/`未开始`/价值/「方案」节（D/H 四要素：做什么/为什么/怎么做/为什么这么做；D-lite 可一行方案一行理由——**用户确认优先级即批准方案**）/范围/不做/可测验收/依赖。
7. **独立审查**：spawn `general-purpose` agent 重载草稿 + 关联模块文档独立评审（实体漂移 / 证伪性 / 边界可辨 / 隐含依赖是否列出），≤2 轮修订。
8. 🔴 **用户确认优先级后才 committed** → 转 Mode B 落档。

轮次：硬上限 5 轮，第 5 轮仍模糊 → 产出当前最佳草稿并显式标注未决缺口；第 3 轮起用户说"够了/开始做吧"可早退。

呈现：各轮面向用户的内容按 CLAUDE.md 原则 13 的场合分野执行——讨论轮叙事优先（结论先行、单例贯穿、术语白话），证据表/行号留给 R/F 审计场景。

## Mode B：backlog 生成

1. 读需求、阶段范围、相关模块文档。
2. **清晰度门**：每条候选验收标准必须具体可测；出现套话 → 停下，进 B0；用户坚持 → 记为风险入 item。
3. 提取候选 → 按模块分组 → 草拟优先级 + `未开始` + 「方案」节（分级要求见 `项目约定.md`「Backlog item 格式」）→ 补验收条件。
4. **独立审查**（agent 重载评审：证伪性 / 范围边界 / 依赖完整 / 优先级一致性——P0 跳过是否真阻塞阶段），≤2 轮修订。
5. 🔴 **用户确认优先级后才 committed**。

规则：AI 可草拟；人类定优先级与范围；宁少而可验证，不要碎片化 TODO；无证据不得标 `进行中`/`已完成`。

## Mode C：阶段规划

1. 读控制台 + P0/P1 item；逐项查模糊（见上），模糊项明确标注"须先 B0 澄清再纳入"。
2. 选出相干阶段集 → 执行顺序 → 阶段验收定义 → 排除范围。
3. **独立审查**（依赖图：顺序是否尊重 item 依赖 / 范围连贯：所选是否达成阶段目标 / 阶段验收可否客观验证 / 排除项是否确不阻塞），≤2 轮。
4. 🔴 **用户确认后才实施**。

输出含：阶段目标 / 纳入范围 / 不纳入范围 / 执行顺序 / 阶段验收 / 风险 / 待确认事项。

## Mode G：阶段过渡

1. 读控制台 + 阶段范围 + backlog 摘要；汇总已完成基线能力；按 blocker 分类列未决阻塞（待产品决策/待技术方案/待外部依赖/待验证）。
2. 从缺口/阻塞/用户目标提炼 1–3 个下阶段主题候选。
3. 🔴 **人类选定下阶段目标后**才生成下批编号 backlog（模块与 backlog 同号新建）。
4. 目标或活跃 backlog 变化后才更新控制台。

规则：阶段完成不自动开工；不静默扩范围；优选 1–3 个连贯主题；旧 backlog 保持历史，新工作建新 item。

## Mode H：高风险共识（仅路由判定为高风险时加载）

Planner → Architect → Critic 循环（**最多 5 轮；Architect 与 Critic 必须串行 await**）：

1. 只载目标 item + 关联模块文档 + 相关代码区，不读全库。
2. **Planner** 出计划：受影响文件与模块 / 数据流变更 / 迁移策略 / 测试策略 / 回滚方案 / RALPLAN-DR 摘要（Principles 3–5、Decision Drivers top 3、Viable Options ≥2 含 pros/cons）。
3. **Architect** 审：架构契合 / 耦合风险 / 安全与数据完整性；**必须给最强反方论证（steelman antithesis）+ 至少一个真实权衡冲突**。
4. **Critic** 按质量标准评：验收可测且被计划覆盖 / 备选公平考虑 / 风险有缓解 / 验证步骤具体；强制原则-选项一致性。
5. 任一非 APPROVE → 收集反馈修订 → 重跑 Architect → Critic；5 轮未过 → 带剩余风险呈现最佳版。
6. 🔴 **共识批准** → 计划文件即执行指南 → 转 Mode D；持续拒绝 → 问用户：照做 / 缩 scope / 延期。

成功：计划含 ADR（Decision / Drivers / Alternatives / Why chosen / Consequences / Follow-ups）；验收标准被计划覆盖；执行前用户已批准。

## 规划类失败处理

- **B/B0 critic 不过**：逐条修订重提 ≤2 轮；仍不过 → unresolved 项在 backlog 中显式标注，按用户决定继续。
- **H 5 轮未 APPROVE**：展示最佳版 + Architect/Critic 最后反馈 → 🛑 STOP，用户三选一。
