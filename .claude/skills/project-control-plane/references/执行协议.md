# 执行协议：Mode D / D-mini / D-lite / D-Chain

进入前已完成路由（SKILL.md）。本协议含必答清单、执行步骤、同步矩阵（唯一权威）与失败处理。

**按 Mode 读节**（三 Mode 互斥，只读当前模式 + 共用节）：
- 共用：编码前必答清单 + 同步矩阵 + 失败处理协议
- 进 D → 加「Mode D：执行单个 item」
- 进 D-mini → 加「Mode D-mini：微小行为修复」（无需必答清单——准入四条件已覆盖）
- 进 D-lite → 加「Mode D-lite：小行为修复」
- 进 D-Chain → 加「Mode D-Chain：持续运行」

## 编码前必答清单（未答完不写代码）

1. 此改动会让哪个已有文档描述变错？→ 搜 docs/modules/、当前实现总览、设计总览 → 先更新它们。
2. 涉及新设计决策？（选型/流程变更/边界约定/架构关系）→ 先更新设计总览或模块文档。
3. 需要未来追溯原因？→ 建 backlog item（例外：纯 typo/空格/颜色微调，且不改任何 API/行为/数据/文档描述）。
4. CHANGELOG 记了吗？→ 每条挂在 `## YYYY-MM-DD` 日期标题下；当天无标题先创建；每次改动一行，不做判断。
5. **关联字段有效吗？**→ item 的关联计划/关联代码/关联模块文档路径必须存在或显式写 `—`（见 `项目约定.md`「关联字段有效性」）；禁止"待建"占位长期残留。
6. **验收状态诚实吗？**→ 置 `已验收` 前核对：验收条件全勾 + 状态记录有实测通过闭合 + backlog 状态非"未开始"（见 `项目约定.md`「伪完成判定」）。

## 同步矩阵（唯一权威——收尾核对与任何状态同步都以此为准）

| 变更 | 更新 |
|------|------|
| 阶段状态 / 活跃项 / blocker 变化 | `docs/项目控制台.md`（只汇总不存详情，单行 ≤200 字符，见 `项目约定.md`「控制台与索引行规则」） |
| **item 验收闭合** | 四处同步：① 模块 backlog 索引行更新状态 ② 控制台**删除**该项（不留划线） ③ `CHANGELOG.md` 一行 ④ 设计总览能力地图该模块行（仅当模块能力有增减时） |
| 任何代码改动 | `CHANGELOG.md`（带日期，一行即可） |
| 设计决策（选型/流程/边界/架构） | `docs/设计总览.md`（活文档；更新单位=能力地图一行或决策一节，不重写整文档） |
| 模块行为/范围/流程变化 | 对应 `docs/modules/*.md` 的「关键功能怎么做」节 —— grep 变更符号（视图名/URL 路径/模板文件）找全部引用处，全更新 |
| 验收条件/实现状态变化 | 对应 `docs/backlog/*.md` |
| 只读审计报告 | `plans/` 或独立报告文件；不改模块文档 |
| 仅测试修复 | backlog/plan 即可；不改模块文档 |
| 同步前基线 | 先跑 `python .claude/skills/project-control-plane/scripts/check-sync.py` 建立漂移基线，收尾后再跑一次确认对齐 |

## Mode D：执行单个 item

1. 按上下文包加载（`项目约定.md`）：目标 item + 关联模块文档 + 相关代码与测试。
2. **必答清单**（见上，未答完不写代码）。
3. **清晰度核对**：目标一句话说得清？边界/不做/依赖明确？每条验收标准可测（能指到具体文件/测试/行为）？已读调用方与被调方？
   - item 缺「方案」节 → **立项补齐再实现**（D/H 四要素：做什么/为什么/怎么做/为什么这么做，见 `项目约定.md`「Backlog item 格式」；D-lite 一行方案一行理由）。方案节应在 B0/B 立项时已具备，此处为兜底。
   - 任一不清晰且非链模式 → 出「待确认问题清单」问用户；链模式 → 记为风险继续。
4. **风险分类**：高风险（P0 / 跨模块 / 安全认证 / 数据迁移 / >20 文件 / API 破坏）。链模式且未获"自己处理高风险项"授权 → 停链报告；已授权或标准风险 → 继续。
5. 建/更新 `plans/<date>-<id>-<task>.md`；item 置 `进行中`。
6. 最小改动实现。
7. **四层验证**（循环）：
   a. **自检**：每条验收标准收集新鲜证据（跑测试、读输出）；失败继续实现，不跳标准。
   b. **Reviewer 独立验证**（按具体验收标准，不是"是否完成"）：<5 文件且 <100 行 → 标准档（sonnet）；5–20 文件 → 标准档（sonnet）；>20 文件或安全/架构类 → 深度档（opus）。拒绝 → 修复重提直到通过；通过后同轮进入 c，不停顿汇报。链模式：每 3 个 item 批量一次 audit（标准档；批次含高风险用 opus 档）。
   c. **Deslop**：`Skill("ai-slop-cleaner")` 只扫本轮改动文件。链模式与 reviewer 同批量。
   d. **回归**：重跑相关测试 + build + lint，读输出确认通过；失败修复重跑。
8. **按同步矩阵更新**（含 item 状态+状态记录、控制台、模块文档 grep、OpenAPI/DB 文档、设计总览、CHANGELOG）；项目要求时更新代码图。**收尾三问（防内容漂移——行为描述是否失实 check-sync 查不到，靠这里）**：
   - ① 本次改动改变了模块行为或能力？→ 模块文档「关键功能怎么做」节与设计总览能力地图该模块段是否已同步改写（不是只加变更记录一行）；
   - ② 产生新的关键决策（选型/边界/机制）？→ 设计总览「仍在生效的关键设计决策」或模块文档决策节补一条（含为什么、否决过什么）；
   - ③ 新增模块/页面/数据表？→ 设计总览能力地图、文档导航、模块文档表设计节收录。
   任一答「不确定」一律视为「需更新」。**收尾跑 `python .claude/skills/project-control-plane/scripts/check-sync.py`** 确认无 HIGH（孤儿引用/状态漂移/计数漂移/能力地图断链）；有则修后再提交。
9. **汇报**（三件套 + 附加）：已完成 / 修改文件 / 验证四层结果 / 未完成与风险 / 建议下一步。区分本轮改动 vs 既有脏工作区 vs 暴露的旧问题。从 Mode R 进入时，先归并修复队列（P0 正确性 / P1 测试文档一致性 / P2 清理）再开工。
10. **意外发现**（范围遗漏 / 代码与 backlog 假设冲突 / 未声明依赖 / 验收覆盖不到的实现细节）→ 记入 item 状态记录。链模式不停，链尾做一次轻量回溯：列出全部意外发现，建议对受影响 item 走 B0 澄清或直接更新。

## Mode D-mini：微小行为修复（合法路径零变化，2026-09-29 用户拍板分级）

**全部满足才用**：①合法路径行为不变（只影响非法/边缘输入的处理方式）②grep docs/ 与模块文档无已记录行为契约被推翻 ③≤5 文件 ④非安全认证/DB 迁移/API 破坏/跨模块。

流程：直改 → 定向验证（合法路径正例 + 非法输入路径反例各一次）→ **CHANGELOG 一行**（commit message 详根因——git 历史即追溯，不建 item 不建 plan）。

事后升级：用户后续报告相关问题时，凭 git 历史补 backlog item 转正常流程，不为小概率预付全流程成本。

## Mode D-lite：小行为修复

**全部满足才用**：入口进入；单模块 ≤3 文件；无 schema/API 破坏/安全/跨模块重构/外部状态变更；成功标准具体可证伪。

流程：读控制台 + 相关文件 → 必答清单 → `plans/<date>-<task>.md`（问题/方案/风险/验证）→ **必须建 backlog item**（唯一例外：纯 typo/空格/颜色且不改任何契约）→ 最小修复 → 定向验证（既有失败与新增分开记录）→ CHANGELOG。

## Mode D-Chain：持续运行

1. 读控制台，所有 `未开始` 的 P0→P1→P2 item 按优先级 + ID 序作队列。
2. 逐项走完整 Mode D，不等确认；完成（含「已完成」状态更新）即加载下一项上下文继续，只输出一行过渡：`BL-XXX 完成（X files, ruff/mypy/pytest/tsc ✓）。开始 BL-YYY。`
3. 停止条件：队列全 `已完成` / 遇高风险且未授权自处理 / 用户打断 / 不可恢复错误（DB 不可达、依赖缺失等）。
4. 环境服务崩溃（PostgreSQL/Redis/Meilisearch/uvicorn/Celery）→ `pg_isready`/`redis-cli ping` 检查 → 自动重启后继续；重启失败 → 🛑 STOP 链，输出已完成 item 清单 + 崩溃服务名 + 修复命令建议。
5. reviewer + deslop 批量：每 3 个 item 一次，不跳过。
6. 全链完成 → 按同步矩阵核对 → 输出汇总（每 item 状态/验证结果/修改文件数）→ 建议 Mode F 并给验收证据清单。

## 失败处理协议（确认 → 修复 → 重试 → 上报）

- **偏离计划**：实际操作偏离已声明计划/承诺 → 向用户说明差异并等待指示，不静默继续、不自我批准。
- **测试失败**：记录 exact command + 失败测试 + 摘要 + 判定 pre-existing 或本轮引入 + 建议下一步；修复重跑。
- **reviewer 拒绝**：逐条修 → 重验 → 重提（≤3 轮）；仍不过 → 理由记入 plan，item 留 `进行中`（阻塞：待技术方案），汇报用户。
- **deslop 引入回归**：git diff 定位 → 逐条回滚问题清理 → 重跑测试；兜底回滚整个 deslop commit，记录"deslop 跳过（引入回归）"。
- **控制台不存在**：首次使用则创建最小控制台（阶段名/backlog 索引/活跃项/阻塞项）；仍无信息 → 问用户阶段与优先级，引导 Mode B。
- **item 缺 scope/验收**：查关联模块文档补全；仍无信息 → 标记模糊，路由至 B0；兜底：`进行中` + 记录"范围待澄清" + 汇报后继续下一项。
- **上下文不足**：列出具体缺口（"不知 API 响应格式""不知 DB 表结构"）逐项 grep；仍不足 → 🛑 STOP，列缺口清单等用户补充。
- **git 失败**（脏 worktree/冲突）：`git stash` → 重试；兜底：备份改动到 `/tmp/`，告知用户后继续。
- **必答清单某条无法确定**：grep 受影响文档/符号 → 列清单；不确定默认标"需更新"，实现后按同步矩阵验证。
